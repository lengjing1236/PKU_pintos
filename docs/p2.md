#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
>How do you avoid overflowing the stack page?

我在 `setup_stack(void **esp, const char *cmdline)` 中完成参数传递，步骤如下：

1. 先分配并映射一页用户栈，初始 `*esp = PHYS_BASE`。  
2. 将 `cmdline` 复制到临时缓冲区，用 `strtok_r` 按空格切分，得到 `argv[0..argc-1]`。  
3. 按 **逆序** 将参数字符串压栈（从 `argv[argc-1]` 到 `argv[0]`），并记录每个参数在用户栈中的地址 `arg_addrs[i]`。  
4. 对齐栈指针到 4 字节边界。  
5. 压入 `NULL` 作为 `argv[argc]` 哨兵。  
6. 再按逆序压入各参数地址，使得最终 `argv[0]` 在最低下标位置，用户程序看到的顺序正确。  
7. 依次压入 `argv`（即 `char **`）、`argc`、假返回地址 `0`。

之所以能保证 `argv[]` 顺序正确，是因为“字符串逆序压栈 + 指针逆序压栈”组合后，在内存中恢复为正序索引。

避免栈溢出的策略：
- 用户栈仅映射一页，参数复制时单参数最大按页限制处理；
- 使用固定上限数组（如 `argv[128]`）限制参数个数；
- 通过 `strlcpy(..., PGSIZE)` 限制命令行长度；
- 压栈过程遵循页大小边界，避免无界写入。

#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` 使用静态全局状态，不可重入，也不线程安全。内核和用户程序场景中可能存在并发解析或嵌套调用，`strtok_r()` 由调用者显式提供 `save_ptr`，可重入、线程安全，更适合操作系统内核实现。

>A4: In Pintos, the kernel separates commands into a executable name and arguments.  In Unix-like systems, the shell does this separation.  Identify at least two advantages of the Unix approach.

Unix 由 shell 解析参数的优点包括：

1. **职责分离更清晰**：内核只负责 `execve` 装载与执行，不关心复杂命令行语法。  
2. **功能更灵活**：重定向、管道、通配符、变量替换等都由 shell 扩展，不需修改内核。  
3. **内核更小更稳定**：减少内核字符串解析逻辑，降低错误与攻击面。  
4. **可替换性更强**：不同 shell 可实现不同解析策略，而不影响内核接口。

>B1: Copy here the declaration of each new or changed struct or struct member, global or static variable, typedef, or enumeration.  Identify the purpose of each in 25 words or less.

与系统调用相关的数据结构如下：

1. `struct file_desc`（见 A1）  
用途：每进程文件描述符项，保存 fd 与 `struct file*` 的绑定关系。

2. `struct thread` 新增字段（见 A1）

- `fd_list`：保存当前进程所有打开文件；

3. `syscall.c`：
```c

```
用途：保护 `create/remove/open/read/write/close/...` 等文件系统操作。

4. `struct child_status` 与 `children_list/self_stat`（见 A1）  
用途：支持 `exec/wait/exit` 的父子同步与状态回收。

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

本实现采用“每进程独立 fd 表”：

- `open` 成功后创建 `file_desc` 节点，分配 `fd = next_fd++`，插入当前线程的 `fd_list`。  
- 后续 `read/write/filesize/seek/tell/close` 通过 `find_fd(fd)` 在**当前进程**内查找对应 `struct file *`。  
- `close` 删除映射并关闭文件对象。  
- 进程退出时遍历 `fd_list` 全部关闭。

因此，文件描述符只在**单个进程内部唯一**，不同进程可以出现相同 fd 数值。

#### ALGORITHMS

>B3: Describe your code for reading and writing user data from the kernel.

核心策略是“访问前验证 + 失败即终止进程”：

1. `fetch_int()`：读取系统调用号与参数前，检查 `uaddr` 和 `uaddr+3` 映射有效。  
2. `check_cstr()`：逐字节调用 `get_user_byte()`，直到 `'\0'`，任何字节无效则 `exit(-1)`。  
3. `check_ubuf(buf,size)`：逐字节检查用户缓冲区，处理跨页边界场景。  
4. `sys_read/sys_write` 在实际拷贝前调用检查函数，确保用户地址可访问。  
5. 无效地址统一调用 `exit_with_status(-1)` 结束当前用户进程，避免内核崩溃。

此外，在 `exception.c` 的 `page_fault()` 中对内核态访问用户地址异常做恢复处理：将返回寄存器置为 `-1`，用于支持 `get_user` 风格的安全探测。

>B4: Suppose a system call causes a full page (4,096 bytes) of data
>to be copied from user space into the kernel.  What is the least
>and the greatest possible number of inspections of the page table
>(e.g. calls to pagedir_get_page()) that might result?  What about
>for a system call that only copies 2 bytes of data?  Is there room
>for improvement in these numbers, and how much?

按我当前实现，`check_ubuf()`是逐字节检查，每字节会触发一次基于映射/访问的合法性验证（通过 `get_user_byte` 路径）。

- 拷贝 4096 字节：最少和最多都接近 4096 次检查（线性按字节）。  
- 拷贝 2 字节：最少和最多约 2 次检查。  

改进空间：可以改为“按页检查”：
- 对每个跨越到的虚拟页只做一次 `pagedir_get_page()`，然后页内直接拷贝。  
- 这样 4096 字节在同一页时可降到 1 次（从 O(n) 到 O(页数)），2 字节通常也可降为 1 次。  
- 这会显著减少检查开销，但实现复杂度略高（需要处理页边界和末尾字节）。

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

`wait` 基于 `child_status` 实现：

1. 父进程在 `process_execute` 为子进程创建 `child_status` 并维护在 `children_list`。  
2. `process_wait(child_tid)` 先在 `children_list` 中查找该子进程；找不到返回 -1。  
3. 找到后在 `exit_sema` 上等待，直到子进程退出时 `sema_up`。  
4. 读取 `exit_status` 后，将该节点从父进程列表移除并减少引用计数。  
5. 子进程 `process_exit` 中写入退出状态、唤醒父进程、减少自身引用计数。  
6. 通过 `ref_cnt` 保证父/子任一方先退出都不会造成悬挂指针或泄漏。

>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

我采用“分层封装 + 统一失败出口”的策略：

1. 将用户地址校验封装为基础函数：`check_uaddr / fetch_int / check_cstr / check_ubuf`。  
2. 系统调用主体只表达业务逻辑，先检查参数，再执行操作，避免业务代码被大量错误处理淹没。  
3. 对指针错误统一执行 `exit_with_status(-1)`，由线程退出路径统一回收进程资源。  
4. 对需要加锁的路径采用“小临界区”原则：进入文件系统前加锁，尽快释放锁，降低异常路径复杂度。  
5. 对局部资源（如 `open` 后但 `fd` 分配失败）在同一函数内立即清理，避免泄漏。

示例：`sys_open` 中，先验证字符串，再持有 `filesys_lock` 调用 `filesys_open`，若 `fd_get` 失败则立即 `file_close(f)`，最后统一释放锁并返回错误码。

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

在 `process_execute` 中，父进程创建子线程后立刻对 `child_status.load_sema` 执行 `sema_down()` 阻塞等待。  
子线程在 `start_process` 调用 `load()` 后，把结果写入 `child_status.load_success`，再 `sema_up(&load_sema)` 唤醒父进程。  
父进程被唤醒后检查 `load_success`：
- 成功：返回子进程 tid；  
- 失败：返回 `TID_ERROR`（`exec` 对应 -1）。

因此 `exec` 返回时机严格晚于子进程装载完成。

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

同步机制依赖 `child_status + exit_sema + ref_cnt`：

1. **P 先 wait，C 后退出**：  
   P 在 `exit_sema` 阻塞；C 退出时写 `exit_status` 并 `sema_up`，P 被唤醒后回收父侧引用。

2. **C 先退出，P 后 wait**：  
   C 已写好状态并发信号，P 进入 wait 后可立即获取退出码并回收父侧引用。

3. **P 未 wait 就退出，C 仍运行**：  
   P 在 `process_exit` 遍历 `children_list`，释放父侧引用；C 未来退出时释放子侧引用，最后自动释放 `child_status`。

4. **P 未 wait 就退出，C 也已退出**：  
   双方引用都可在各自退出路径中递减到 0，状态对象最终释放。

特殊情况：
- 非子进程调用 `wait` 返回 -1；
- 对无效 tid 调用 `wait` 返回 -1；
- 通过引用计数避免父子退出先后带来的 UAF/重复释放问题。

#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

我选择“显式校验 + 异常兜底”的方式，原因是：

1. 逻辑直观：在 syscall 入口即可看见参数合法性检查；  
2. 容易调试：出错路径集中到 `exit(-1)`；  
3. 与 Pintos 测试（尤其 boundary/bad-ptr）匹配良好；  
4. 代码可维护性较好：校验逻辑复用，系统调用主体更清晰。

缺点是逐字节检查效率不高，但在 Lab2 规模下可接受，并可在后续按页优化。

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

优点：
1. 设计简单、符合 Unix 抽象（fd 与内核对象分离）；  
2. 进程隔离明确，不同进程互不影响；  
3. 易于在 `process_exit` 统一回收全部打开文件；  
4. 与 `exec_file`（deny write）机制兼容。

缺点：
1. 当前用链表查找 fd，`O(n)`，大量打开文件时效率一般；  
2. `next_fd` 单调递增，不复用空洞，长期运行会使 fd 值变大；  
3. 全局文件系统锁粒度较粗，并发性能有限。

>B11: The default tid_t to pid_t mapping is the identity mapping.
>If you changed it, what advantages are there to your approach?

本实现未修改默认映射，采用 `pid == tid`。  
优点是实现简单、调试方便、与线程创建接口天然一致；在 Lab2 阶段可减少额外抽象带来的错误。若后续扩展到多线程进程模型，再引入独立 PID 命名空间会更合适。
